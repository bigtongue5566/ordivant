# Run console, workflows, Agent templates and execution isolation

Revision: 2026-10-07. This document governs the user-selected F03, F04/F13 and F05 implementation. Python Work owns business authorization, durable controls and workflow state; Pi owns transcripts. Public clients never receive service credentials.

## Delivery scope

Run inspection and controls, immutable Agent/workflow templates, dependency-aware automatic dispatch with manual/interval triggers, project-scoped external MCP connections, and per-run Docker workspaces with file and command tools. Independent result review remains mandatory. Every page must use real API state and distinguish DEMO from live receipts.

## Ownership and additive storage

PM owns this contract, root Compose/helpers, integration checks and final acceptance. Backend worker owns `backend/**`; runtime worker owns `runtime/**` and new `sandbox/**`; UI worker owns `frontend/src/**`. Workers must not change another owner's files. New tables hold run state/events/controls, Agent execution settings, template versions, workflow definitions/instances/steps, tool connections and sandbox profiles. Existing databases must start and retain their data without destructive migration.

## Run console

`Run` is distinct from a business `Execution`. Run id equals its dispatch/outbox id. Public shape: `{id,project_id,task_id,agent_id,execution_id:null|string,status:"queued"|"running"|"paused"|"done"|"failed"|"aborted",desired_action:null|"pause"|"resume"|"stop",control_revision:number,retry_of:null|string,mode:"demo"|"live"|null,model_config:null|ModelSelection,receipt:null|RunReceipt,answer:null|string,error:null|string,created_at,updated_at,started_at:null|string,finished_at:null|string,sandbox:null|object}`. `done` means the model turn was submitted; task acceptance still requires independent review. Unknown usage/currency stays null.

`RunReceipt` uses the existing runtime shape: `{mode:"demo"|"live",requested:ModelSelection|null,returned:{provider_id:string,model_id:string}|null,usage:{input_tokens:number|null,uncached_input_tokens:number|null,cached_input_tokens:number|null,cache_write_tokens:number|null,output_tokens:number|null,total_tokens:number|null}|null,tools:[{name:string,calls:number}],cost_usd:null}`. Input includes uncached/cache read/cache write. Returned identity and usage are actual completion observations, never copied from requested metadata and labelled measured.

- `GET /api/runs?project_id=&task_id=&status=` returns scoped runs, newest first, max 200.
- `GET /api/runs/{id}` returns a scoped Run.
- `GET /api/runs/{id}/events?after_sequence=0` returns ordered events `{sequence,kind,created_at,data}`. Keep at most 1000 bounded, sanitized events per run. Kinds include start, model, tool_start, tool_end, error, control, status and sandbox. Never store tool authentication, lease tokens, provider keys or arbitrary request headers.
- `POST /api/runs/{id}/control` body `{action:"pause"|"resume"|"stop"|"retry"}`; authorized project manager/admin only, idempotent. Returns Run for controls, new Run for retry. Pause is cooperative: it prevents the next tool operation (or queued admission), while the dispatcher renews the same valid execution lease. Already active model/tool calls can finish. `desired_action=pause` is a pending request; `status=paused` is reported only when the gate is actually waiting. The UI explains that the Run pauses before its next tool operation. Resume opens that gate for the same submission/execution only while ownership is valid. Pi 1.0.3 has no public pause API: do not simulate pause by aborting and relabeling a terminal submission. Global timeout includes paused time. Stop immediately fences/releases any running business execution, leaves the task ready, then requests actual runtime abort/cleanup. Cancelling a task also prevents pending admission and stops its active run. A pending stop must prevent a new claim. Retry accepts terminal failed/aborted runs whose task is ready; it creates a fresh dispatch/run and later a fresh execution, recording `retry_of`. It never silently reopens a reviewed/done task. Conflicting lifecycle operations return 409.
- `GET /api/runtime/runs/controls?worker_id=` is runtime-only, restricted to owned/authorized runs. Returns `{id,desired_action,control_revision}` records; no human endpoint proxies arbitrary URLs or exposes runtime credentials.
- `POST /api/runtime/runs/{id}/sync` body `{worker_id,delivery_token,sequence,status,execution_id?,mode?,receipt?,answer?,error?,events?:[{kind,data}],sandbox?}`. Verify current outbox ownership/fence and project/organization; tolerate identical delivery sequence idempotently, reject stale owners. `done` requires that the linked execution actually submitted an artifact; a review racing ahead of terminal sync (accept or reject) does not undo that submission. A pending stop cannot turn into `done`. Dispatcher confirms the idempotent business submit before terminal sync; a rejected/unconfirmed submit must never be presented as success. Persist only safe public metadata. A stopped outbox retains its fence until abort reporting/ack so actual state can be reconciled. Terminal delivery credentials are revoked; an exact terminal sync reply-loss replay still validates the original worker and token fingerprint.
- Dispatcher processes control revisions while a run is active, including paused runs. Abort/resume paths and process restart recheck business ownership. The private fenced runtime handoff may return `execution_lease:null|{task_id,execution_id,agent_id,lease_token,expires_at}` for the Run's already-linked, still-running, unexpired execution that the same Agent and task still own. The Python transaction rotates its lease token and hands the new token only to that authorized worker; stale tokens remain invalid. The dispatcher matches the persistent execution id and uses that lease during recovery rather than replaying an obsolete cached claim token. No lease/provider/tool credentials are written to Pi or RunStore. If a recovered checkpoint has lost or expired its execution, mark failure with an actionable reason; never resume with a stale lease. Limits always apply to live and demo generation.
- Runtime serializes each Run's lease-sensitive Python callbacks with renewal. Progress, release and scoped platform mutations capture the current token inside that queue; they cannot race a rotation and fence their own valid execution. Final submission captures its immutable body only after progress, heartbeat stop and queued renewals finish. External MCP/sandbox calls and model requests do not hold this queue, so lease heartbeats can continue during them.
- Terminal Run synchronization waits for the engine's cleanup to settle and reads a fresh stored record; an early model `done` must not publish a stale workspace `ready` snapshot. Successful executor deletion reports `stopped`; unconfirmed deletion reports sandbox `failed` plus a fixed sanitized error. A recovered terminal record whose temporary workspace was still marked available reports sandbox `lost` and an explicit cleanup-unconfirmed error. The model result is not replayed, and credentials/capabilities are never restored from persistence.

## Agent execution settings and immutable templates

`ExecutionConfig`: `{instructions:string,tool_connection_ids:string[],sandbox_profile_id:null|string,limits:{max_turns:number,timeout_seconds:number}}`. Instructions <=16000 chars; defaults empty instructions/no external connections/no sandbox, 20 turns and 600 seconds; configurable bounds 1..100 turns and 30..3600 seconds. Backend checks every referenced resource and model selection.

Agent create/edit/list add `execution_config:ExecutionConfig` and `template_id:null|string` (exact immutable version id). Creating with `template_id` applies its definition; explicit execution/model overrides are validated. Editing configuration does not change an existing run. Dispatch stores non-secret execution/model/tool/profile snapshots. Runtime receives connection authentication only in the existing fenced, no-store configuration handoff and never saves it to Pi/store. Template changes affect only newly applied versions.

`AgentTemplate`: `{id,key,version,name,description,definition:{role:"worker"|"reviewer",capabilities:string[],instructions:string,model_config:null|ModelSelection,tool_connection_ids:string[],sandbox_profile_id:null|string,limits:{max_turns,timeout_seconds}},created_at}`.

Built-ins also expose read-only `builtin_key:"pm"|"pg"|"sa"|"sd"|"qa"|"reviewer"|null`. Startup backfills six v1 templates for existing organizations; new organizations receive them at creation. Repeated initialization preserves existing data. Custom templates and derived versions return null; only exact built-in versions are localized in the interface. PM/PG/SA/SD/QA use worker and Reviewer uses reviewer, with no model, tool, or Sandbox binding.

- `GET /api/agent-templates` lists visible organization versions; mutations manager/admin only.
- `POST /api/agent-templates` body `{key,name,description?,definition}` creates v1; duplicate key conflicts.
- `POST /api/agent-templates/{id}/versions` body `{name,description?,definition}` publishes a new immutable version of that key. Earlier versions remain unchanged. Parallel publication must not duplicate version numbers.
- Existing `POST/PATCH /api/agents` supports applying the exact `template_id` and manual settings; one-time Agent credential rules remain unchanged. UI exposes templates, instructions, tool bindings, sandbox profile and run limits in both creation and editing.

## Workflows and automatic dispatch

`WorkflowStep`: `{key,title,goal,description:string,acceptance_criteria:string[],dependency_keys:string[],agent_id:null|string,capabilities:string[],reviewer_id:null|string,priority:"urgent"|"high"|"medium"|"low"}`. 1..20 steps, unique keys, acyclic dependencies, same-project/scoped agents and reviewers. Explicit agent or deterministic worker-capability selection; unavailable/busy agents cause waiting, not invented results. No automatic self-review.

`Workflow`: `{id,project_id,key,version,name,description,steps:WorkflowStep[],schedule:{enabled:boolean,interval_minutes:number,max_runs:number},next_run_at:null|string,created_at}`. Definition/steps are immutable versions; schedule is separately editable. Interval 1..525600 minutes; scheduled max_runs 1..1000. `WorkflowInstance`: `{id,workflow_id,project_id,status:"running"|"waiting"|"completed"|"failed"|"cancelled",trigger:"manual"|"schedule",inputs:string,steps:[{key,task_id,status,run_id:null|string,error:null|string}],created_at,updated_at}`. Each instance pins its workflow version, stores stable task ids and only completes after all steps are independently accepted. Blocked/failed work is visible and recoverable, never reported as accepted.

- `GET/POST /api/workflows?project_id=`; creation body `{project_id,key,name,description?,steps,schedule?}`.
- `POST /api/workflows/{id}/versions` publishes definition `{name,description?,steps}`; same key/project, immutable previous version.
- `PATCH /api/workflows/{id}/schedule` body `{enabled,interval_minutes,max_runs}` manager/admin only.
- `POST /api/workflows/{id}/start` body `{inputs?:string}` manager/admin, idempotent; returns instance with exactly one task per step and task dependency ids. Text inputs are bounded; no arbitrary code/interpolation eval.
- `GET /api/workflow-runs?project_id=`; `GET /api/workflow-runs/{id}`.
- `POST /api/workflow-runs/{id}/cancel` `{}` manager/admin; cancels unfinished tasks/runs using the same fencing/control service.
- `POST /api/runtime/workflows/tick` `{}` scoped runtime only. Atomically admits due schedules without overlap/catch-up storms; claims workflow scheduling state so concurrent ticks produce one set of tasks/outbox records. Dispatches ready steps only when dependencies are done and an allowed Pi worker is available (including outstanding dispatch reservations). Periodic dispatcher calls make accepted upstream steps advance without manual dispatch. Do not require Knowledge/Code services to run.
- MCP adds thin scoped wrappers for run inspection/control, template/workflow inspection/start and tool/profile inspection, using the same REST/business authorization and idempotency.

## Project tool connections

First adapter is official MCP Streamable HTTP. No arbitrary host subprocess/stdio launcher. Connections are project-scoped; runtime registers only explicitly allowed, discovered tools. Tool names exposed to Pi are namespaced to avoid platform tool collisions. External tool replay is unsafe by default and cannot be silently retried after an uncertain side effect.

`ToolConnection`: `{id,project_id,name,endpoint,enabled,allowed_tools:string[],key_configured:boolean,created_at,updated_at}`. Mutation body `{project_id?,name,endpoint,enabled,allowed_tools,auth_token?:string}`; optional/blank token preserves the encrypted secret. Endpoint changes require explicit new credential when one is configured. Secrets are write-only, encrypted using the Work key, excluded from audit/idempotency cache/errors. Admin configures connections; project-scoped members may list safe metadata/use authorized bindings.

- `GET/POST /api/tool-connections?project_id=`; `PATCH /api/tool-connections/{id}`.
- `POST /api/tool-connections/{id}/test` `{}` admin only -> `{ok:true,tools:[{name,description,input_schema}]}` or explicit safe failure, no fake fallback. Read-only tools/list protocol check, not arbitrary execution. Limit response and duration.
- Operator environment `ORDIVANT_TOOL_ALLOWED_HOSTS` explicitly permits exact endpoint hosts; HTTP additionally requires `ORDIVANT_TOOL_HTTP_HOSTS`, and DNS resolving to private/non-global addresses requires `ORDIVANT_TOOL_PRIVATE_HOSTS` in every mode. Default empty denies external endpoints. Reject userinfo/fragments/redirects and non-HTTP(S) schemes. Apply policy on save, probe and each runtime connection; internal QA fixture host is separately allowed in all three lists only in QA. HTTPS private services still require valid TLS. API bodies cannot bypass host policy.
- Dispatch fails clearly for disabled/missing bound connections. Bindings are filtered to the executing project; cannot inherit access from another project. Fenced handoff adds `execution_config` and `tool_connections:[{id,name,endpoint,allowed_tools,auth_token:null|string}]` plus `sandbox_profile` snapshot. Model selection, execution settings and MCP/profile snapshots are immutable for the admitted Run. Provider credentials are resolved through the existing private model handoff and current provider availability policy; they are not frozen into a public snapshot or Pi storage.

## Per-run execution sandboxes

`SandboxProfile`: `{id,project_id,name,enabled,limits:{timeout_seconds:number,memory_mb:number,cpu_count:number,pids_limit:number,output_bytes:number,workspace_mb:number},created_at,updated_at}`. Policy is fixed: no network, fixed operator-provided job image, non-root, read-only root filesystem, dropped capabilities, no-new-privileges, no host bind mounts/socket/secrets. Limits bounded: timeout 1..120s, memory 64..1024 MiB, CPU 0.25..2, pids 16..128, output 1024..65536 bytes, workspace 1..128 MiB. A per-run tmpfs workspace survives its commands only for that run; result file/test content must be captured as evidence before cleanup. Restart loses ephemeral workspace and is reported explicitly.

- `GET/POST /api/sandbox-profiles?project_id=`; `PATCH /api/sandbox-profiles/{id}` admin only writes, authorized scoped reads.
- Sandbox runtime tools: `sandbox_write_file(path,content)`, `sandbox_read_file(path)`, `sandbox_list_files(path?)`, `sandbox_execute(command:string[],timeout_seconds?)`. Only relative workspace paths; prevent traversal/symlink escapes. Command is argv, never host shell. For shell syntax an explicit `/bin/sh -lc` runs inside the isolated job. All outcomes carry exit_code/stdout/stderr/truncated/duration; failure and timeout must remain visible and cannot be converted into a passing test.
- New `sandbox-api` on internal 8040 uses its own generated service secret and durable ownership metadata. Only this trusted executor holds the Docker daemon socket; runtime and web never do. Executor accepts bounded create/command/file/stop calls with run ownership/capability fencing. Jobs have unique names, owner labels and isolated tmpfs workspace; commands/file access are serialized per run. Limit concurrent jobs. Cleanup on run completion/abort/timeout and service restart; only delete executor-owned labelled jobs. No caller-selected image, mounts, network, environment, Docker flags or privilege.
- Executor endpoints: `GET /health`; `POST /sandboxes` `{run_id,profile:{limits}}` -> `{run_id,status:"ready",token}` one-time per-run capability; `POST /sandboxes/{run_id}/execute` `{command,timeout_seconds?}`; `POST /sandboxes/{run_id}/files/write` `{path,content}`; `POST /sandboxes/{run_id}/files/read` `{path}`; `POST /sandboxes/{run_id}/files/list` `{path?:"."}`; `DELETE /sandboxes/{run_id}`. Service bearer protects creation; returned per-run bearer protects run operations. Work authorization occurs before runtime handoff. No sandbox secret may enter model tool arguments/transcripts or public status.
- Root supplies `compose.sandbox.yaml`, `-WithSandbox` helper (requires Work/runtime), generated `sandbox_service_token`, image build and explicit local Docker isolation checks. Existing installations with sandboxes disabled remain usable. Private deployment requires operator control of the trusted executor/daemon; container isolation is not a VM boundary.

## Required acceptance

Run controls: queued stop prevents admission, live/demo interrupt resumes safely, stale lease cannot submit, stopped/retried records stay separate, duplicate controls/ticks do not duplicate work, receipt/events survive service restart and cross-project access is denied. Templates: immutable version/application snapshot, creation/edit persistence. Workflows: manual plus interval trigger, parallel ticks exactly once, capability waiting, dependency/review separation and cancellation. Tools: actual MCP tools/list and tool call against a synthetic fixture, allowlist enforcement, encrypted/no-store secrets and project denial. Sandboxes: real file/write/read and successful/failing commands, cross-run file denial, traversal/symlink rejection, timeout/resource/network isolation, abort/restart cleanup. UI: real API mouse flows and desktop/390px popups. Validate isolated QA before updating the main local containers; preserve human accounts and main IdP/model settings.
