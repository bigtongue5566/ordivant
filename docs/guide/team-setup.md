# 團隊設定：人員、角色、範圍與登入 {#team-setup}

本指南說明 Identity 管理員如何為團隊準備 Work、Knowledge 和 Code。三個產品可以共用人員登入，但各產品仍會分別檢查自己的角色與資源範圍。

## 了解初始管理員與一般成員 {#admin-and-members}

每個環境都有獨立的 Identity 服務和帳號資料。首次使用時，第一位使用者建立唯一的初始管理員帳號。系統沒有預設帳號或密碼。請安全保存一次性復原碼。

管理員可以管理人員和邀請。一般成員只能使用明確授予的產品角色，並存取明確授權給他們的 Work 專案、Knowledge Space 或 Code 專案。同一個帳號能登入三個產品，不表示自動取得全部權限。

## 邀請成員並授予存取權 {#invite-and-scope}

1. 以管理員身分登入，在姓名旁開啟「帳號與安全性」。
2. 開啟「使用者與邀請」，選擇「新增邀請」。輸入成員姓名和電子郵件。Suite 角色保留為「成員」；只有需要管理使用者和組織權限的人才選「管理員」。
3. 在產品權限編輯器中選擇需要的產品角色和確切資源範圍：

   | 產品 | 角色 | 資源範圍 |
   | --- | --- | --- |
   | Work | 管理者、工作者或審核者 | 一個或多個 Work 專案 |
   | Knowledge | 管理者、編輯者或讀者 | 一個或多個 Knowledge 空間 |
   | Code | 管理者、編輯者或讀者 | 一個或多個 Code 專案 |

4. 選擇「建立邀請」。系統只顯示一次邀請碼，並顯示有效期限。若 Identity 已設定 SMTP，系統會寄送一次性邀請郵件；未設定時不會寄信，請透過獲准的安全管道交付邀請碼。確認安全交付後再關閉對話框。
5. 受邀者在登入頁選擇「接受邀請」，輸入邀請碼並自行設定密碼。登入後應只看得到授權範圍內的資源。

授予完成工作所需的最小角色和範圍。如果看不到專案或 Space，管理員應編輯該成員的「產品角色與資源」。一個產品的角色不會授權另一個產品的存取權。

## 保持人員之間的獨立審查 {#independent-review}

需要審查的工作至少安排兩個人：一位有權限的人提交證據，另一位有權限的 Reviewer、Manager 或 Admin 審查。服務會拒絕提交者審查自己的成果。

建立或編輯 Work 任務時，管理者可在「負責者」選擇此 Project 已授權的真人同事或 Agent；「指定審核者」也可選真人或 Agent。未指定負責者時，合資格的真人 Worker、Manager 或 Admin 可直接認領。真人只能認領未指派或指派給自己的任務，不能代領同事工作。管理者可指派受邀且已啟用、但尚未首次登入 Work 的同事；此人完成邀請並登入後即可處理。

真人可直接以自己的 Work 帳號回報進度、提交證據、標記受阻或交接，不需要建立 Agent、啟用 Agent Runtime 或設定 LLM。重新載入後，可從任務執行紀錄繼續真人工作。交接並釋出會結束目前執行、記錄交接並清除真人負責者，讓其他合資格同事認領；受阻或被退回的工作則保留原負責者。Agent 自動執行仍使用 Agent 專屬租約和 fencing token。完整步驟見[Work 指南](work.md)與[第一個專案教學](first-project.md#manual-route)。

## 分開人員、Agent 與 Runtime 身分 {#separate-identities}

瀏覽器帳號是人員的 Identity 工作階段。Agent 有自己的角色和明確的產品資源範圍。Pi Durable Runtime 使用獨立的機器身分接收獲准的工作。這些身分不會互相繼承權限：邀請人員不會授予 Agent 專案存取權，啟用 Runtime 也不會讓它取得不受限的業務權限。

建立 Agent 前先選取目標 Work 專案；新 Agent 會獲准存取該專案。確認它出現在該專案的 Agent 名錄中。建立 Agent 時可能只顯示一次其範圍憑證；若部署需要，請只將憑證保存在指定 Runtime 設定。不要將憑證貼進任務、當成人員登入分享或寫入日誌。Pi Durable 會透過已設定的 Runtime 處理內部 Agent 交接。

## 停用或恢復成員 {#disable-restore}

開啟「帳號與安全性 → 使用者與邀請」。使用成員的「啟用」開關停用存取；該帳號現有的登入工作階段會被撤銷。要恢復存取，再開啟此開關。成員需要重新登入，且仍受管理員授予的產品角色和資源範圍限制。當前登入的管理員不能在此頁停用自己的帳號；需要另一位管理員處理。

權限變更時，也請檢查該成員另外管理的 Agent、程式碼儲存庫、模型供應商或外部工具存取權。這些身分和憑證獨立於人員帳號管理。

## 連結企業 SSO {#connect-sso}

Identity 管理員開啟「帳號與安全性 → 企業 SSO」，設定組織的 OIDC Provider。頁面會提供要登記在身分服務的 Callback URL。填入 Issuer URL、Client ID、Client Secret、允許網域和成員佈建政策，儲存並選擇「測試連線」。為受邀或佈建的成員設定明確的產品角色和資源範圍；電子郵件網域相同本身不會授予專案存取權。

要連結既有本機帳號，在同一頁使用「明確連結既有帳號」。選取「Ordivant 帳號」，填入身分服務提供的穩定「企業 subject（sub claim）」，再選擇「連結企業帳號」。該帳號首次企業登入時，電子郵件仍須與既有帳號相符。只因電子郵件相同不會合併帳號。請在清單確認連結；解除連結會撤銷受影響的企業登入工作階段。

啟用 SSO-only 政策前，先測試一般成員的登入、資源存取和登出，並保留管理員復原入口。Direct OIDC 支援 Entra ID、Google Workspace、Okta、Auth0、Keycloak 和通用 OIDC。SAML 與 LDAP／Active Directory 可透過選用的 Keycloak broker 連線。供應商設定細節請見[企業登入與身分管理](../enterprise-sso.md)。

## 排查存取問題 {#team-access-troubleshooting}

| 畫面狀況 | 檢查方式 |
| --- | --- |
| 無法接受邀請 | 確認代碼輸入正確、仍在 24 小時有效期限內且尚未使用。過期或已使用的邀請碼需要重新建立邀請。 |
| 登入成功但產品無法使用 | 檢查帳號是否啟用，以及是否有該產品的角色和資源範圍。 |
| 可以開啟產品但看不到某個專案或 Space | 在「產品角色與資源」中將該資源加入成員範圍。 |
| Reviewer 無法審查任務 | 確認他有該 Work 專案的 Reviewer、Manager 或 Admin 權限範圍、不是提交者，且與任務指定的真人或 Agent 審核者相符。 |
| SSO 登入成功但沒有資源 | 檢查成員佈建政策、群組角色對應和明確的專案／Space 範圍。僅驗證身分不會授予資源存取權。 |

權限準備完成後，請接著看[第一個專案](first-project.md)。完整角色說明見[管理員指南](administration.md)。
