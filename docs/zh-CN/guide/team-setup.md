# 团队设置：人员、角色、范围与登录 {#team-setup}

本指南说明 Identity 管理员如何为团队准备 Work、Knowledge 和 Code。三个产品可以共用一个人员登录，但每个产品仍会分别检查自己的角色和资源范围。

## 了解初始管理员与成员 {#admin-and-members}

每个环境都有独立的 Identity 服务和账号资料。首次使用时，第一位用户创建唯一的初始管理员账号。系统没有默认账号或密码。请安全保存一次性恢复码。

管理员可以管理人员和邀请。普通成员只能使用明确授予的产品角色，并访问明确授权给他们的 Project、Space 或 Code Project。账号能登录三个产品，不会因此自动取得三个产品的权限。

## 邀请成员并授予访问权 {#invite-and-scope}

1. 以管理员身份登录，在姓名旁打开「账号与安全性」。
2. 打开「用户与邀请」，选择「添加邀请」。填写成员姓名和电子邮件。Suite 角色保留为「成员」；只有确实要管理用户和组织权限的人才选择「管理员」。
3. 在产品权限编辑器中，选择所需的产品角色和准确资源范围：

   | 产品 | 角色 | 资源范围 |
   | --- | --- | --- |
   | Work | 管理者、工作者或审核者 | 一个或多个 Work Project |
   | Knowledge | 管理者、编辑者或读者 | 一个或多个 Knowledge Space |
   | Code | 管理者、编辑者或读者 | 一个或多个 Code Project |

4. 选择「创建邀请」。系统只显示一次邀请码，并显示有效期。Identity 设置 SMTP 后会发送一次性邀请邮件；未设置时不会寄信，请通过获准的安全渠道交付邀请码。确认安全交付后再关闭对话框。
5. 受邀者在登录页选择「接受邀请」，输入代码并自行设置密码。登录后应只能看到授权中包含的资源。

授予完成工作所需的最小角色和范围。如果项目或 Space 没有显示，管理员应编辑该成员的「产品角色与资源」。一个产品中的角色不会授权另一个产品的访问权。

## 保持人员之间的独立审核 {#independent-review}

需要审核的工作至少安排两个人：一位有权人员提交证据，另一位有权的 Reviewer、Manager 或 Admin 审核。服务会拒绝提交者审核自己的结果。

创建或编辑 Work 任务时，Manager 可以在「负责者」中选择此 Project 已授权的真人同事或 Agent；「指定审核者」也可选择真人或 Agent。未指定负责人时，符合条件的真人 Worker、Manager 或 Admin 可以直接认领。真人只能认领未指派或指派给自己的任务，不能代领同事的任务。Manager 可以先将任务指派给已受邀且已启用、但还没有首次登录 Work 的同事。

真人可直接使用自己的 Work 账号回报进度、提交证据、标记受阻或交接，不需要创建 Agent、启用 Agent Runtime 或配置 LLM。重新加载页面后，可从任务执行历史继续真人工作。「交接并发布」会结束当前执行、记录交接并清除真人负责人，让其他符合条件的同事认领；受阻或被退回的任务仍保留原负责人。Agent 自动执行仍使用 Agent 专属租约和 fencing token。完整步骤见[Work 指南](work.md)与[第一个项目教程](first-project.md#manual-route)。

## 分开人员、Agent 与 Runtime 身份 {#separate-identities}

浏览器账号是人员的 Identity 会话。Agent 有自己的角色和明确的产品资源范围。Pi Durable Runtime 使用单独的机器身份接收获准工作。这些身份不会互相继承权限：邀请人员不会授予 Agent 项目访问权，启用 Runtime 也不会让它获得不受限的业务访问权。

创建 Agent 前先选中目标 Work Project；新 Agent 会获准访问该 Project。确认它显示在该 Project 的 Agent 名录中。创建 Agent 时可能只显示一次其范围凭证；若部署需要，请只把凭证保存在指定的 Runtime 配置中。不要把它贴进任务、当成员登录分享或写入日志。Pi Durable 会通过已配置的 Runtime 处理内部 Agent 交接。

## 停用或恢复成员 {#disable-restore}

打开「账号与安全性 → 用户与邀请」。使用成员的启用开关停用访问；该账号现有的登录会话会被撤销。要恢复访问，再打开此开关。成员需要重新登录，且仍受管理员所授予的产品角色和资源范围约束。当前登录的管理员不能在此页面停用自己的账号；需要由另一位管理员处理。

权限变更时，也请检查该成员另行管理的 Agent、代码仓库、模型供应商或外部工具访问权。这些身份和凭证独立于人员账号管理。

## 连接企业 SSO {#connect-sso}

Identity 管理员打开「账号与安全性 → 企业 SSO」，配置组织的 OIDC Provider。页面会提供需要注册到身份服务的 Callback URL。填写 Issuer、Client ID、Client Secret、允许的域名和成员配置政策，保存并测试连接。为受邀或配置的成员设置明确的产品角色和资源范围；匹配电子邮件域名本身不会授予项目访问权。

要连接既有本地账号，在同一页面使用「明确链接既有账号」。选择「Ordivant 账号」，填写身份服务提供的稳定「企业 subject（sub claim）」。该账号首次企业登录时，电子邮件仍须与既有账号相符。只匹配电子邮件不会合并账号。请在列表核对链接；解除链接会撤销受影响的企业登录会话。

启用 SSO-only 策略前，先测试普通成员的登录、资源访问和退出，并保留管理员恢复入口。Direct OIDC 支持 Entra ID、Google Workspace、Okta、Auth0、Keycloak 和通用 OIDC。SAML 与 LDAP／Active Directory 可通过选用的 Keycloak broker 接入。供应商配置详见[企业登录与身份管理](../enterprise-sso.md)。

## 排查访问问题 {#team-access-troubleshooting}

| 现象 | 检查方式 |
| --- | --- |
| 无法接受邀请 | 确认代码输入正确、仍在 24 小时有效期内且未使用。过期或用过的代码需要重新创建邀请。 |
| 登录成功但产品不可用 | 检查账号是否启用，以及是否有该产品的角色和资源范围。 |
| 产品可打开，但看不到某个 Project 或 Space | 在「产品角色与资源」中将该资源加入成员的范围。 |
| 审核者无法审核任务 | 确认其有此 Work Project 的 Reviewer、Manager 或 Admin 权限范围、不是提交者，并且与任务指定的真人或 Agent 审核者相符。 |
| SSO 登录成功但没有资源 | 检查成员配置政策、群组角色对应关系和明确的 Project／Space 范围。只验证身份不会授予资源权限。 |

权限准备完成后，请继续看[第一个项目](first-project.md)。完整角色说明见[管理员指南](administration.md)。
