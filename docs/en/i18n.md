# Language and translation

The documentation site is available in Traditional Chinese, English, and Simplified Chinese. Switching languages opens the corresponding version of the same article. The selected documentation language is part of the URL, so it remains selected after a reload or when you bookmark the page. `docs/.vitepress/public-pages.json` explicitly lists user guides and their three locale versions. Markdown outside this list is excluded from the site, search index, and sitemap.

The application UI supports Traditional Chinese, English, and Simplified Chinese. The choice is saved in same-origin browser storage under `localStorage` key `ordivant.locale` and synchronized across tabs. Changing the UI language does not reload the page or clear forms. Before a choice is saved, the application checks `navigator.languages`: `zh-TW`, `zh-HK`, and `zh-MO` select Traditional Chinese; other Chinese locales select Simplified Chinese; English locales select English; unsupported locales fall back to Traditional Chinese.

Language selection changes the application UI, documentation navigation and search, and documentation text. Ordivant does not automatically translate user-created Work projects or tasks, Agent instructions, messages, Knowledge documents, Code content, or model responses. These items remain in the language their authors used; users and Agents choose the language that suits their work.

## Developing application translations

Application translations live in `frontend/src/i18n`. The locale identifiers are `zh-TW`, `zh-CN`, and `en`. Traditional Chinese UI copy is the source key; English translations are stored in `catalogs/*.en.ts`, and Simplified Chinese translations are stored in `catalogs/*.zh-CN.json`. Source keys and `t()` from `useI18n()` are for UI copy only. Do not use them to translate user-authored content.

Components use `useI18n()` to subscribe to the current locale and get `t()`. When an error or status message must be kept in React state, store its source text and interpolation values with `localized(source, values)`, then pass it to `t()` when rendering. This lets the message follow locale changes without losing its meaning or values. Forms use `useLocalizedForm(form)`. On a locale change, it revalidates only fields that already have errors; it does not submit the form, clear drafts, or reset field values.

```sh
npm --prefix frontend run i18n:check
```

Contributors write and review both English and Simplified Chinese translations directly; translations are not generated by converting Chinese characters. When adding or changing a Traditional Chinese source key, update the matching entries in both catalogs for that module. Translate meaning using natural regional terminology, and preserve API identifiers and interpolation tokens such as `{{name}}`.

`i18n:check` reads catalogs without changing them. It detects missing, blank, non-string, obsolete, or conflicting entries and mismatched interpolation tokens, and exercises language switching with the actual translation files. It does not generate or overwrite translations. Meaning and terminology still require editorial review.

After adding or changing UI translations, check the catalogs and build all four frontend modes, then inspect the changed screens in a regular local development environment:

```sh
npm --prefix frontend run i18n:check
npm --prefix frontend run build:suite
npm --prefix frontend run build:work
npm --prefix frontend run build:knowledge
npm --prefix frontend run build:code
```

After changing public documentation, build the translated pages and check public links and redirect pages:

```sh
npm --prefix docs run i18n:check
npm --prefix docs run build
uv run --project backend --no-sync python scripts/check_docs.py
node scripts/build_docs_redirects.mjs
```

For browser verification, run `npm --prefix docs run preview` and open the local preview. Check the changed article in all three locales, corresponding paths after language switching, heading anchors, search results, and mobile layout. Confirm that only articles on the public allowlist appear on the site.

## Contributing translations

The Traditional Chinese pages in the `docs/` root are the current source. Other languages use the same relative paths: for example, `docs/guide/work.md` corresponds to `docs/en/guide/work.md` and `docs/zh-CN/guide/work.md`. Only articles listed in `docs/.vitepress/public-pages.json` are published. Add a public article's relative path without a locale prefix, such as `guide/work.md`, to the list and create its three locale files. Other files remain in the public source repository but are excluded from the site, search, and sitemap; this is publication scope, not access control.

- Follow the Traditional Chinese source and keep features, limits, numbers, and security statements consistent.
- Keep commands, API paths, environment variables, code, JSON examples, product names, and stable technical identifiers unchanged.
- Preserve relative links, heading anchors, image paths, and code blocks across versions. Check links when adding or moving headings.
- Compare the source and both other languages when updating a translation; do not update only navigation and the home page while leaving guides or contracts behind.
- Build the documentation and run `scripts/check_docs.py`. List the source pages and languages updated in the pull request.

When a translation is incomplete, identify the missing language version explicitly. Do not use an untranslated page in another language as a substitute.

## Checking documentation body {#checking-document-body}

`i18n:check` checks headings, paragraphs, tables, locale counterparts, and matching section IDs across all Markdown in the repository, including pages that are not published. The documentation site build includes only the explicit public allowlist. Untranslated English prose on Chinese pages and Chinese prose on English pages fail the check. Commands, code, API identifiers, and product names remain unchanged. Every listed article must have Traditional Chinese, Simplified Chinese, and English versions.

```sh
npm --prefix docs run i18n:check
npm --prefix docs run build
uv --cache-dir .cache/uv run --project backend --no-sync python scripts/check_docs.py
```

Browser verification should cover the changed public article in all three languages and check visible text, language switching, search, section bookmarks, and mobile navigation. Automated checks detect missing translations; translators must still compare all three versions for accurate behavior, limits, and terminology.

## Documentation publishing {#documentation-publishing}

The documentation site is published at the organization's root domain, <https://ordivant-ai.github.io/>, using GitHub Pages from `ordivant-ai/ordivant-ai.github.io`. Article source lives in `ordivant-ai/ordivant`; GitHub Actions checks and builds pages from its public allowlist. Application services are deployed separately.
