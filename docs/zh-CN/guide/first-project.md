# 第一个项目：从上线清单到验收结果 {#first-project}

本教程带你从首次登录走到同事指派、真人认领、Knowledge 共同编辑和独立审核。示例项目是「产品上线准备」（`LAUNCH`），任务名称为「整理产品上线清单」。三个产品的真人流程都不需要 LLM，也不必创建 Agent 来代表同事。后面的模型和自动 Agent Run 是可选功能。

## 开始之前 {#before-you-begin}

打开管理员提供的平台网址。如果你要自行安装，请先完成[安装指南](../containers.md)，再打开本地或组织网址。Work、Knowledge 和 Code 的常规真人操作不需要模型密钥。Pi Durable Agent 自动 Run 才需要管理员启用 Runtime 并配置供应商和模型；Code 的 Git repository 与 PR 功能需要管理员配置 Gitea 服务。

![Ordivant 登录页面](/screenshots/login-zh-CN.png)

## 以管理员或受邀成员身份登录 {#sign-in}

全新环境由第一位使用者打开工作区并选择「创建管理员账号」。填写姓名、电子邮件、至少 12 个字符的密码并再次确认，然后提交。请安全保存一次性恢复码。系统没有默认账号或密码。

如果管理员邀请了你，在登录页选择「接受邀请」，输入管理员交给你的一次性邀请码，再自行设置密码。邀请码 24 小时后过期且只能使用一次。使用 SSO 的成员通过企业登录按钮进入。登录本身不会授予所有产品或项目的访问权；参见[团队设置](team-setup.md)。

## 创建发布项目 {#create-project}

1. 在产品切换器中选择 **Work**。在项目选择器中选择「创建项目」。只有 Identity 管理员可以创建 Work 项目。
2. 填入以下值：

   | 字段 | 示例 |
   | --- | --- |
   | 项目代码 | `LAUNCH` |
   | 项目名称 | `产品上线准备` |
   | 描述 | `规划、跟踪和审核产品发布前需要完成的工作。` |
   | 团队 ID | 除非管理员提供了真实团队 ID，否则留空。 |
   | 预算上限 (USD) | 除非组织使用项目预算，否则留空。 |

3. 提交「创建项目」。项目选择器和页面标题应显示 `LAUNCH` 与「产品上线准备」。

如果你是普通成员而无法创建项目，请让管理员创建项目，并授予 Work 角色和项目范围。选择 Work 本身不会授予访问权。

## 可选：添加带版本的 Knowledge 规范 {#knowledge-specification}

如果发布要求需要负责人、版本历史和可追踪来源，可以使用 Knowledge；这一步是可选的。

1. 切换到 **Knowledge**。Identity 管理员选择「添加 Space」，使用代码 `LAUNCH`、名称「产品上线准备」和简短描述创建空间。随后由管理员给相关人员授予 Knowledge 角色及该 Space 范围。
2. 选择 `LAUNCH` Space，再选择「添加文档」。例如标题填写「上线准备规范」，摘要填写「首次上线审核所需的要求与证据」，标签填写 `launch` 和 `readiness`。
3. 在「正文（Markdown）」中输入真实规范，包括决定、负责人、日期和已知来源材料。适当添加来源引用的标签和 URI，然后选择「创建文档」。阅读画面应显示 `v1`、正文与来源引用。
4. 创建文档后，打开最新版本的「共同草稿」并选择「编辑」。Writer 和 Manager 可以一起修改正文，并切换「预览」检查格式。在线列表显示已登录的共同编辑成员；Agent 也可通过 REST 或 MCP 参与同一草稿。草稿显示「已连接」和「已保存」后，选择「发布新版本」，填写变更摘要并确认。这会创建不可变版本，已发布内容不能修改。

Reader 可以查看共同草稿与版本历史，但不能编辑。如果连接中断，服务器未确认的修改只保存在当前浏览器标签页的内存中；不要关闭或重新加载标签页。发布出现版本冲突时，重新加载共同草稿，检查最新合并内容，修改后等待显示已保存，再发布。来源 URI 仅作为引用；填写 URI 不会自动读取或导入页面内容。共同编辑细节见[Knowledge 指南](knowledge.md)。

## 可选：为 Agent 自动 Run 配置模型连接 {#configure-model}

人工路线可以跳过本节。只有 Identity 管理员可编辑组织模型连接。请向供应商或部署管理员确认受支持的 HTTPS API base URL 和准确的模型 ID。请直接在表单输入自己从供应商取得的密钥；不要从指南复制密钥、把密钥放入任务或发送给 Agent。

1. 在 **Work** 中打开「模型连接」。
2. 选择「添加 Provider」，填写唯一的 Provider ID、显示名称、供应商的「HTTPS API base URL」，并在「API Key」中输入自己的密钥。例如网址格式可能是 `https://api.example.com/v1`；此示例域名只是占位值，并非可用供应商。
3. 根据供应商提供的信息添加模型 metadata：准确的 Model ID、显示名称、上下文窗口、最大输出 tokens 和支持的推理强度，然后启用 Provider。
4. 打开组织默认模型，选择 Provider 和 Model 并保存。创建 Pi Agent 时应可选到该模型。已保存的密钥不会再次以明文显示；只有更换密钥时才输入新值。

![模型连接设置](/screenshots/models-zh-CN.png)

若没有配置可用的供应商或模型，派发的 Run 可能标记为 **DEMO**。DEMO 使用确定性的演示回复，不会调用付费模型，也不会生成真实发布交付物。不要把演示结果或回报成本当成已完成任务。参见[模型连接](../model-usage.md)与[Run 和自动化使用指南](../execution-usage.md)。

## 可选：在此项目中创建 Pi Durable Agent {#create-agent}

只有需要自主 Agent 执行任务时才完成本节；真人同事可直接被指派或认领，不需要 Agent。Identity 管理员或 Work Manager 可以管理 Agent。先确认 Work 当前选中的项目是 `LAUNCH`；创建表单会授予 Agent 当前选中项目的访问权。Agent 表单中没有 Project 字段。

1. 打开「Agent 名录」并选择「添加 Agent」。
2. 名称填写 `Launch checklist worker`；「Agent 角色」选择「运行者」，「Runtime」选择「Pi Durable」。若团队尚未发布合适的不可变模板，则留空「Agent 模板版本」。
3. 在「能力标签」添加 `launch-readiness`、`research`、`documentation` 等能力。除非管理员提供了真实 ID，否则「团队 ID」留空。
4. 在「模型设置」中继承组织默认值，或选择已配置的覆盖模型。确认有效模型是预期的供应商与模型，然后选择「创建 Agent」。

Agent 应以可用状态显示在此项目的名录中。为其他项目创建 Agent 前，先确认当前选中项目。Agent 身份和 Runtime 身份与人员登录分开；授予成员的项目权限不会自动授予 Agent。平台会将受范围限制的 Agent 凭证交给 Runtime，以执行获准的 Run。

## 按明确规格创建任务 {#create-task}

打开「任务」并选择「添加任务」。这是自包含的合成练习，不需要 API、外部系统或公司资料。将「合成练习数据」中的 8 行复制到「输入资料」字段。

### 合成练习数据 {#practice-background}

```text
合成练习，仅供操作演示：以下是虚构数据，不需要 API 或外部来源。
产品：Northstar 练习版；上线日期：尚未确认。
产品：发布范围与负责人尚未提供；请确认；负责人未分配。
登录：当前登录设置与验证证据尚未提供；状态未知。
备份：备份负责人、最近备份记录和恢复证据尚未提供；状态未知。
文档：需要起草发布说明；文档负责人和当前文档链接未分配。
支持：支持负责人、服务时段和升级联系人尚未提供；状态未知。
分析：成功指标、事件映射和仪表板证据尚未提供；状态未知。
```

这组练习数据刻意保留未知信息；不要编造日期、负责人、批准或测试结果。

| 任务字段 | 可复制的示例 |
| --- | --- |
| 任务名称 | `整理产品上线清单` |
| 描述 | `为计划中的产品发布准备一份可审核的清单。` |
| 目标 | `找出发布准备工作、负责人、状态和证据，让审核者可以判断发布前还剩下什么。` |
| 输入资料 | 复制上方「合成练习数据」区块中的 8 行内容。 |
| 范围 | `以已提供的合成练习资料为来源，为产品、登录、备份、文档、支持和分析各写一行清单。每行都要包含事项、负责人、状态和下一步行动。` |
| 限制条件 | `不得编造负责人、日期、批准或完成状态。不得更改发布计划或外部系统。不得包含凭证或个人资料。` |
| 验收条件，每行一项 | `清单各包含产品、登录、备份、文档、支持和分析六个领域。`<br>`每项都有负责人，或明确标记为未分配。`<br>`每项状态都有来源支持，或标记为未知。`<br>`每个未完成事项都有下一步行动。`<br>`提交结果包含清单以及审核所需的链接或引用证据。` |
| 优先级 | `一般` |
| 负责人 | 选择已获授权此 Project 的真人同事，或留空供符合条件的同事认领。仅在需要自动 Run 时选择 `Launch checklist worker`。 |
| 指定审核者 | 选择另一位有权限的真人或 Agent。允许任何合资格人员审核时可留空。 |
| 依赖任务 | 除非必须先接受其他任务，否则留空。 |

选择「创建任务」。未指派的任务应以「待运行」状态出现在清单中。打开任务检查目标与验收条件。真人负责人可以直接选择「认领任务」；如果任务指派给同事，则由该同事登录并处理自己的任务。任务抽屉分为「规格」、「执行与审核」、「协作」和「事件」视图。

![任务规格和执行控制](/screenshots/task-zh-CN.png)

### 工作依赖其他任务时添加前置条件 {#task-dependencies}

先创建前置任务，例如「确认发布日期和发布范围」，并说明哪些证据可证明它已通过。编辑清单任务，在「依赖任务」中选择这个前置任务；提示文字说明被选任务必须先完成。前置任务获接受前，依赖任务不能认领或派发。前置任务获接受后，符合条件的后续任务会解除阻塞并进入「待运行」。不要建立循环依赖。

## 可选：派发 Agent 并检查 Run {#dispatch-and-run}

真人流程可跳过本节。具备权限的 Work Manager 或 Admin 打开「待运行」任务，在「选择 Pi 运行 Agent」中选择 `Launch checklist worker`，然后选择「派发给 Agent」。这会创建自动 Run，需要先配置 Provider 和 model。「认领任务」由同事本人执行，不会启动自动 Run。

打开「Run 运行」并选择新 Run。检查状态、进度、事件、回复、工具和回报的模型／用量凭据。真实供应商调用应在 Run 记录中标明配置的模型。如果 Run 显示 DEMO，请勿把其回复当成发布证据；改用人工路线或先配置模型。

Run 完成与任务验收是两件事。只有任务已提交结果、至少一个证据成果物，而且状态为「待审核」，才继续审核。如果 Run 结束但没有提交证据，就还不能审核；Worker 必须通过任务执行流程提交摘要和证据。

![Run 详情和事件记录](/screenshots/run-zh-CN.png)

## 提交并独立审核证据 {#submit-review}

提交者提供简洁的完成摘要和至少一项证据，例如文件、网址、测试报告或摘要。任务随后进入「待审核」。打开任务的「执行与审核」视图，逐项对照验收条件检查成果和来源。

具备权限且不是提交者的 Reviewer、Manager 或 Admin 选择「通过」或「退回任务」，填写审核意见并确认。通过后任务变为「已完成」，也可能解除后续任务的阻塞。退回会保留提交内容、历史记录和原负责人。提交者不能审核自己的结果。真人或 Agent 都可以作为指定审核者。

![独立审核任务证据](/screenshots/review-zh-CN.png)

### 无 LLM 的真人协作路线 {#manual-route}

真人直接使用自己的账号；本流程不需要创建或选择 Agent、启用 Runtime 或配置模型。在 Identity 中邀请第二位成员，并授予 Work Worker 或 Manager 角色及 `LAUNCH` Project scope。邀请和范围步骤见[团队设置](team-setup.md)。

任务可以指派给这位同事，或留空让同事认领。登录者只能认领未指派或指派给自己的「待运行」任务。真人工作不会过期，重新加载后可以从任务的执行历史继续。

1. 第二位受邀成员打开 `LAUNCH` Project 中的任务并选择「认领任务」。需要时回报进度，也可以在「协作」中记录问题、交接和决议。
2. 在任务执行控制中选择「提交成果」。填写完成摘要，将「证据类型」设为「文档」，填写证据标题，再把下方六行清单粘贴到「证据内容」。至少提交一项成果物，任务应进入「待审核」。
3. 由另一位获授权的 Reviewer、Manager 或 Admin 打开「执行与审核」，逐项检查验收条件和证据，填写审核意见后选择「通过」或「退回」。审核者不能是提交者本人。

如果当前负责人要交给其他同事，选择「交接并发布」，填写已完成事项、未完成项目和下一步。任务会回到「待运行」并清除真人负责人，让其他合资格同事认领。受阻或被退回的任务保留原负责人。

可复制的证据内容（每个领域一条 Markdown 清单）：

```markdown
- [ ] 产品：发布范围和负责人待确认；负责人未分配、状态未知；下一步是确认范围和负责人。
- [ ] 登录：登录设置和验证证据未提供；负责人未分配、状态未知；下一步是取得获准的设置和证据。
- [ ] 备份：负责人、最近备份记录及恢复证据未提供；负责人未分配、状态未知；下一步是取得备份和恢复记录。
- [ ] 文档：需要起草发布说明；负责人未分配、状态未知；下一步是指定文档负责人并提供草稿。
- [ ] 支持：负责人、服务时段和升级路径未提供；负责人未分配、状态未知；下一步是确认支持安排。
- [ ] 分析：成功指标、事件映射和仪表板证据未提供；负责人未分配、状态未知；下一步是确认指标和证据。
```

提交字段示例：摘要 `已根据合成练习数据整理六个上新准备领域；未知状态和未分配负责人均已保留，并列出各项下一步。未访问外部系统，也未宣称测试或批准已经完成。`；证据标题 `Northstar 合成练习上新清单`。独立审核者核对证据后可写：`六个领域均已列出；未知状态和未分配负责人均已保留，且每项都有下一步。这是合成练习，未声称测试通过。`

这条流程由真人账号提交证据并记录作者，不会创建 Pi Run 或调用付费模型。不要把人员密码或 API key 填入任务。

## 复用 Agent 模板或工作流程 {#templates-workflows}

在 `LAUNCH` 项目中打开「自动化」。

- 在「Agent 范本」中，具备权限的 Manager 或 Admin 可选择「添加范本」，定义 key、显示名称、描述、Agent 角色、能力、选用模型、工具、沙箱设置档、指令和运行限制，然后选择「创建 v1」。之后的修改会发布新版本；已有版本和已建立的 Run 保留原快照。从 Agent 名录套用范本会将设定复制到新 Agent。范本本身不会授予项目、模型或工具权限。
- 在「工作流程」中选择「添加流程」，定义每个步骤的 key、名称、目标、描述、依赖、Pi Agent 或所需能力、验收条件及选用的独立审核者，然后选择「创建 v1」。编辑器会检查每个步骤是否指定 Agent 或候选能力。启动实例时选择「手动启动」，在「流程输入」填写本次发布资料，再确认「启动流程」。工作流程会建立任务实例；每一步仍需提交证据并独立审核。可在「运行纪录」查看先前实例。

要复用 Agent 的操作指令，使用模板；要复用一连串有先后关系和审核步骤的任务，使用工作流程。参见[Run 和自动化使用指南](../execution-usage.md)。

## 可选：附加 Code Pull Request {#optional-code-pr}

只有部署已配置 Code 和 Gitea 服务，或组织已将受支持的仓库连到 Work 时才使用。在 **Code** 中选择或创建 Code 项目，必要时创建私人仓库，再建立分支、提交和 Pull Request。该仓库和 PR 应显示在 Code 项目中。创建 Code 项目和仓库需要管理员权限及已配置的 Gitea 连接。

在 Code 项目中选择「添加 Project」，填写项目代码 `LAUNCH`、名称「产品上线准备」和描述。选择「添加私人保存库」，填写储存库名称 `launch-readiness` 和说明；默认建立私人保存库、`main` 分支及 README。选择「创建分支」，从 `main` 创建 `feature/launch-checklist`。选择「提交文件」，在「提交 UTF-8 文件」表单填写「目标分支」、保存库路径 `docs/launch-readiness.md`、「文件内容（UTF-8）」粘贴上方六行清单，以及提交消息 `docs: add launch readiness checklist`。新建文件时在「更新既有文件时的 expected SHA」留空，再选择「创建提交」。选择「创建 PR」，来源分支（Head）填 `feature/launch-checklist`、目标分支（Base）填 `main`，标题填 `Add launch readiness checklist`，描述列出修改内容。创建后 Code 页面应显示该 PR；创建的 `head`／`base` 必须是实际存在的分支。

返回 Work 任务，将 PR 网址作为「网址」证据提交，标题可写 `Launch readiness checklist PR`。审核者可打开 PR，将内容和检查状态与验收条件对照。PR 链接是供审核的证据，本身不会让 Work 任务自动通过。参见[Code 指南](code.md)。

## 完成与常见问题 {#finish-and-troubleshoot}

只有提交了证据并由独立审核者接受，任务才算完成。任务应显示「已完成」；依赖它的任务随后可能进入「待运行」。项目任务清单和总览会反映已接受的状态。

| 画面现象 | 检查方式 |
| --- | --- |
| 项目选择器中没有项目 | 请 Admin 创建 Work 项目，并授予你的 Work 角色和项目范围。 |
| 无法创建 Project、Space 或模型连接 | 创建 Project／Space 和编辑组织模型设置需要 Identity Admin。 |
| 没有可选 Agent | 确认可用的 Worker Agent 是在选中 `LAUNCH` 时建立，且该项目的 Runtime 已启用。 |
| Run 标记为 DEMO | Pi Agent 没有可用模型，或 Pi Runtime 未使用已配置模型。DEMO 不是真实交付物。 |
| 任务受阻或派发被拒 | 检查「依赖任务」，先接受所有前置任务。 |
| Run 结束但任务不在待审核 | 在任务执行视图中检查是否有已提交摘要和证据成果物。Run 完成不等于已提交。 |
| 审核按钮不可用 | 确认审核者有 Work 角色和项目范围、不是提交者；若由人员审核，将「指定审核者」留空。 |
| Knowledge 链接存在但没有正文 | 来源 URI 只是引用。把获准内容加入文件正文，或使用已批准的检索整合。 |
| Code 无法创建仓库或 PR | 请部署管理员确认本环境是否配置 Gitea，并启用了 Code。 |

权限和团队管理请继续阅读[团队设置](team-setup.md)。字段说明见[Work 指南](work.md)。
